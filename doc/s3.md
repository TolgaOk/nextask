# S3 storage

The optional `s3` integration uploads to S3-compatible object storage using
[`minio-go/v7`](https://github.com/minio/minio-go). Hetzner is the initial target.
[Hetzner documents the client and regional endpoint configuration](https://docs.hetzner.com/storage/object-storage/getting-started/using-libraries/#for-go).
It ships in the Nextask binary and requires no separate storage CLI.
Create the destination bucket first. The submitter records the endpoint, bucket,
and file-selection settings; it does not contact object storage during enqueue.

Set credentials in the worker environment before starting it:

```sh
export S3_ACCESS_KEY='your-access-key'
export S3_SECRET_KEY='your-secret-key'
nextask worker
```

Both variables are required for tasks using S3. Missing or blank variables are
named in the error before the task command starts. Use the bucket's S3 credentials. The worker needs permission
to inspect and upload objects, including multipart uploads; automatic region
lookup also needs bucket-location access. Set `region` explicitly when lookup is
unavailable. Credentials are not accepted as integration config keys. Endpoint
and remote URLs must be free of credentials, query strings, and fragments, even
when S3 is not selected.

For example, if only `S3_SECRET_KEY` is missing, the worker reports:

```text
nextask: s3: missing required worker environment variables: S3_SECRET_KEY
```

Run `nextask init db` and upgrade workers before submitting S3 tasks.

## Usage

```sh
nextask enqueue --with s3 './job.sh'
nextask enqueue --with git --with s3 './job.sh'
nextask enqueue --with s3 --set s3.interval=30s './job.sh'
nextask enqueue --with s3 --set s3.interval=0s './job.sh' # final upload only
```

```toml
[integrations.s3]
endpoint = "https://fsn1.your-objectstorage.com"
region = "fsn1"
remote = "s3://my-bucket/my-project"

root = "."
include = ["results/latest.json", "progress/**"]
exclude = ["**/*.tmp", "**/*.partial"]
final_include = ["reports/**", "results/final/**"]

interval = "60s"
final_sync = true
final_timeout = "2m"

concurrency = 4
upload_timeout = "5m"
retries = 3
on_final_error = "fail"
```

Use the endpoint and region for the destination bucket. The same block works in
Nextask user config; shared config uses `[nextask.integrations.s3]`. Configuration
supplies options only. Every task must explicitly select `--with s3`.

```sh
nextask enqueue --with s3 \
  --set s3.remote=s3://my-bucket/exports \
  --set 's3.include=["exports/**","summary.json"]' \
  --set 's3.exclude=["**/*.tmp","exports/cache/**"]' \
  --set s3.interval=30s \
  --set s3.concurrency=2 \
  --set s3.final_timeout=5m \
  './export.sh'
```

The common integration option mechanism accepts typed TOML values. Arrays
use JSON syntax in `--set` and replace the configured list. Repeated assignments
use the last value. Options are validated before preparing resources.

## Options

Every key supports `--set s3.KEY=VALUE`.

| Option | Default | Meaning |
|---|---|---|
| `endpoint` | Required | Object-storage service URL; HTTPS expected |
| `region` | Auto-detect where supported | Provider region |
| `remote` | Required | `s3://bucket/base-prefix`; append the task ID |
| `root` | `.` | Upload root relative to the worker task directory |
| `include` | Empty | Patterns uploaded periodically and at completion |
| `exclude` | Empty | Exclusions applied to every upload pass |
| `final_include` | Empty | Additional patterns uploaded only at completion |
| `interval` | `60s` | Delay between periodic passes; `0s` disables periodic uploads |
| `final_sync` | `true` | Upload after command completion, including failure |
| `final_timeout` | `2m` | Maximum duration of the final upload pass |
| `concurrency` | `4` | Concurrent file uploads; upload passes never overlap |
| `upload_timeout` | `5m` | Per-file time limit, including retries |
| `retries` | `3` | Additional attempts for transient upload failures |
| `min_age` | `0s` | Skip recently modified files during periodic passes; ignored for final upload |
| `max_file_size` | `unlimited` | Optional limit such as `2GiB`; report skipped files |
| `on_final_error` | `fail` | `fail` fails an otherwise successful task; `warn` reports upload failure |
| `symlinks` | `skip` | Skip symbolic links, or use `error` to reject them |

At least one inclusion pattern is required. Final uploads use `include` plus
`final_include`. Exclusions win. Directories named `.git` or `.nextask` are always
excluded at every depth.
Patterns are relative to `root`, use `/` separators, and support `*`, `?`, character
classes, and `**` for nested paths. `root` must stay inside the worker task directory
and cannot traverse symlinks or internal directories. Selected symlinks follow the
`symlinks` policy; directories reached through symlinks are never scanned.

Durations accept Go syntax such as `30s`, `2m`, or `1h30m`, up to `24h`.
Only `interval` and `min_age` accept zero. `concurrency` accepts 1–256 and `retries`
accepts 0–100. A configuration that disables every possible upload pass is rejected.
Missing output directories or no matching files produce an empty successful pass.

## Execution and retention

Enqueue records resolved integration settings with the task. The worker reads
`S3_ACCESS_KEY` and `S3_SECRET_KEY` from its environment at execution time;
credential values stay out of queued commands and configuration diagnostics.

Selected files upload to `<remote>/<TASK_ID>/<relative-path>`. For example,
`remote = "s3://bucket/exports"`, task `export-42`, and file
`reports/result.json` produce `s3://bucket/exports/export-42/reports/result.json`.
Changing `root` changes the filesystem base, not the object prefix. Changed files
replace the same object keys. Nextask creates no directory per upload pass and
performs no automatic remote deletion. Removing a task preserves its stored objects.

Each pass hashes selected files and compares their size and SHA-256 metadata
with the stored object. Identical content is not uploaded again. Selected files
are temporarily staged on worker disk to keep uploaded bytes stable during retries;
staging space is bounded by the files currently being processed (`concurrency`).
Ensure temporary storage has room for those files. Files that change while being
read are reported and retried on the next pass. Write completed output files with
an atomic rename when possible.

Periodic passes run alongside the command, with no overlapping passes. Nextask
reports periodic failures and retries on subsequent passes. Task completion waits
for final sync on command success or failure. Nextask preserves an existing command
failure and applies `on_final_error` to otherwise successful tasks.

Graceful cancellation stops the command and allows a bounded final-upload window.
Each wrapper declares its cleanup time. The task records the combined deadline,
and the worker adds it to its command-stop grace. Runtime wrappers pass inner
cleanup deadlines through when they compose. Cancellation remains cancellation.
`nextask cancel` adds declared cleanup time
to its default confirmation wait; an explicit `--timeout` overrides that wait.
The task is marked finished after finalization. With `worker --rm`, local cleanup
also happens after finalization.
Abrupt instance loss preserves only completed uploads. Uploads do not constitute
an atomic filesystem snapshot.

`nextask remove` does not delete objects. Use the provider's retention/lifecycle
settings or an explicit storage tool to remove them. Provider bucket versioning
may retain previous object versions even though Nextask reuses the same key.
